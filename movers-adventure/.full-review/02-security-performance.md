# Phase 2: Security & Performance Review

## Security Findings

Executive take: this is a static, dependency-free, backend-free client app — no auth, no network I/O, no server code, no eval/Function/document.write, zero third-party dependencies. Most OWASP Top 10 categories don't apply. One real bug class was found (HTML injection via unescaped strings reaching `innerHTML`), correctly downgraded from the Phase-1-flagged "verify this" to **Medium at worst / Low in the intended single-device deployment**, since there's no remote delivery vector — only self-XSS or a same-origin-neighbour-write scenario if ever co-hosted with other content.

### Medium

- **S1 · Unescaped candidate name → `innerHTML` in exam report** (`index.html` source L459, persistence L1887–1888/1924–1925, sink L2023–2024/2048). `maxlength="20"` does not protect: it doesn't constrain programmatic `.value` assignment (line 1924 restores the full stored value from `localStorage` on every visit), and 20 chars is enough for a working payload (`<svg/onload=alert()>`) anyway. `cap()` is a display helper, not an encoder. CWE-79/CWE-602. CVSS 4.7 (`AV:N/AC:H/PR:N/UI:R/S:C/C:L/I:L/A:N`), degrading to Low in the actual one-child-one-device deployment since there's no remote attacker path — only self-XSS or a same-origin-neighbour `localStorage` write. Impact if triggered: abuse an already-granted mic permission via `SpeechRecognition`, or register a service worker for origin persistence — both still require the same-origin foothold that already implies script execution elsewhere. **Fix:** build the untrusted part via `textContent`/`createElement` instead of template-literal `innerHTML`; enforce the 20-char limit in code, not just the attribute; namespace the storage keys (`moversAdventure.candidate` instead of the generic `movers_candidate`) in case of future co-hosting.
- **S2 · Unescaped `localStorage` exam-history `label` → `innerHTML`, no length limit at all** (`index.html` L1889, L1896–1906, sink L1900). Same root cause as S1 but reachable without completing an exam — fires just from opening the Mock Exam home screen — and the `label` field passes through no input element, so there's no length ceiling whatsoever. **Fix:** build history rows via `createElement`/`textContent`; validate/clamp the record shape on load (also closes S3).

### Low

- **S3 · Unvalidated deserialized `localStorage` data → uncaught exceptions (feature-level denial)** (L1889, L1900–1904, L2038). `loadExamHistory()` only try/catches the `JSON.parse` call, not the shape of the result. A malformed record (e.g. `h.slice` undefined, or `'🛡️'.repeat(negativeNumber)`) throws and makes the Mock Exam screen — or a just-completed exam's report — fail to render until storage is cleared. Self-inflicted-or-same-origin only, not a boundary crossing. Fixed by the same rewrite as S2.
- **S4 · No Content-Security-Policy** (no `<meta>` tag present). Would provide defense-in-depth against S1/S2 even if an escaping bug regresses. Complicated by 3 inline `<script>` blocks and 9 inline `onclick` attributes, so a fully strict policy requires refactoring; a partial policy (lock down `default-src`/`connect-src`/`frame-ancestors` while keeping `'unsafe-inline'` on `script-src`) is a one-line, no-refactor improvement.
- **S5 · Always-on, ungated verbose error reporter** (L522, `window.onerror` handler painting raw error text/line numbers in a red bar). Correctly uses `textContent`, not `innerHTML`, so it introduces no injection risk itself — but it's an unconditional debug surface with no gate. Low value as a finding since the entire source is public by construction; recommend gating behind `?debug=1` mainly so children don't see a scary red error bar during normal play (ties to code-quality finding L9 in Phase 1).
- **S6 · Child's name persisted with no notice, consent, or delete path; README contradicts the code.** README states "nothing is persisted to `localStorage`" — no longer true since the exam subsystem added candidate-name and history persistence. Data never leaves the device (no network code exists anywhere), so this is a documentation/UX gap, not a breach exposure. Recommend: fix the README, add a note to the parents' modal, add a "clear my data" control.
- **S7 · Service worker registered from a script (`sw.js`) that does not exist in the repo** (L2066–2069) — informational. Currently inert (registration rejects, silently caught). Worth resolving before it becomes a real concern (broad same-origin scope if ever co-hosted, or a ready-made persistence primitive if script injection is ever achieved via S1/S2).

### Explicitly checked, no findings

SQL/command/LDAP injection (no interpreters), XXE (no XML parsing), broken access control (none to break — the star-based level "gate" is client-side game progression, not a security boundary; a child editing it in devtools is a non-issue), insecure deserialization (only bare `JSON.parse`, no reviver, no prototype-pollution gadget reached), dependency vulnerabilities (zero dependencies — no `package.json`, no CDN scripts), hardcoded secrets/cryptography (none present; `Math.random()` use is appropriate for shuffling/confetti, no security decision depends on it), redirects/path traversal (no `location` writes, no URL/hash parsing). The ~25 other `innerHTML` template-literal sites in the file were traced individually — all interpolate only hardcoded app content (`VOCAB`, `GAP_ITEMS`, etc.), never external/user-influenced data. `SpeechRecognition` transcripts and all exam write-in inputs are handled via `textContent`/string-comparison only, never reach a markup sink — correctly implemented.

## Performance Findings

Executive take: a small, well-structured client-only app — most classic performance categories (DB, bundling, horizontal scale) don't apply. Real findings cluster around two confirmed Web Speech API race conditions with actual on-device impact, and a dead service-worker registration that means ~20KB of double-base64-encoded icon/manifest data gets re-transferred on every single page load with zero caching benefit.

### High

- **P1 · `SpeechRecognition` never `.abort()`ed — orphaned mic sessions with stale-closure callbacks** (confirms/extends Phase 1's architecture finding #9). Verified via grep: zero `.abort()` calls anywhere in the file. `startTalk`/`startCharades` construct a fresh recognizer per round; navigating away (⬅️) before `onresult`/`onerror`/`onend` fires leaves the mic hardware open (battery drain, persistent mic-in-use indicator on some Android browsers) with handlers still closing over the abandoned game's `round`/`score`/`next`. When the delayed result arrives, it can silently overwrite `#gameBody` out from under whatever screen the user has since navigated to. **Fix:** track one reusable recognition instance per game; explicitly `.abort()` and null out its handlers in `backFromGame()`/`goHome()`.

### Medium

- **P2 · `speechSynthesis` queueing race on repeated `say()` calls** — real, reproducible on-device: `say()`'s 70ms deferred-`speak()` workaround (for a Chrome cancel/speak race) means two `say()` calls fired within that window each `cancel()` independently but don't actually cancel each other's pending `speak()`, so utterances queue and play back-to-back instead of the latest replacing the previous. Noticeable to a child mashing the 🔊 replay button, which every mini-game encourages. **Fix:** track the pending speak via a single timer handle so a new call invalidates the previous one, and re-`cancel()` immediately before the deferred `speak()` fires.
- **P3 · Untracked `setTimeout` chains driving round progression** (performance angle on Phase 1's H2/A2 crash bug) — confirmed 11 mini-game call sites never store/clear their timer handle, unlike `renderSequentialMatch` (L1728) which already does this correctly and can serve as the template for the fix. Stray post-navigation timers do wasted `getElementById` lookups against a screen that's moved on, occasionally mutating detached DOM. Bounded (not unbounded growth) but unnecessary work during frequent game-hopping, which is typical for this app's audience.
- **P4 · Dead service-worker registration → no caching benefit for ~20KB of inlined, double-base64-encoded assets.** `sw.js` (registered L2066–2069) does not exist in the directory — confirmed via `ls` — so the registration always rejects, silently swallowed. Consequence: the embedded `apple-touch-icon` (~2.3KB) plus the manifest (which itself re-embeds base64 icons inside base64-encoded JSON — double inflation) together are ~20KB of the file's 130KB (~15%), all re-transferred and re-parsed on every full page load with no cache layer. **Fix (pick one):** ship a real `sw.js` that precaches `index.html` (makes the registration meaningful), or delete the dead registration call; for byte weight specifically, extracting the icons/manifest to real files (`icon-192.png`, `manifest.json`) referenced via normal `<link>` tags would let the browser HTTP-cache them independently of `index.html` edits.

### Low (confirmed but low-impact at this scale)

`allWords()` recomputed on 9 call sites — sub-millisecond even on low-end phones, free to fix via memoization but not worth prioritizing. `pickVoice()` rescans the voice list on every `say()` call — negligible (a few hundred comparisons, called 1-3×/round). Word Hangman rebuilds the full 26-key keyboard on every keystroke via full `innerHTML` — sub-frame at ~30 nodes, a clear example of "full rebuild vs. incremental" but not janky in practice.

### Explicitly checked, no findings (non-issues at this scale)

Event listener leaks — the codebase consistently uses `el.onclick =` property assignment preceded by `innerHTML` teardown, so old listeners are discarded, not accumulated; this is a good existing pattern. DOM node accumulation across replays — every round does a full teardown/rebuild, no stale nodes pile up. Confetti canvas — 90 particles, compositor-friendly Canvas2D work, well within frame budget. CSS animations — all animate only `transform`/`opacity` (compositor-only, no layout thrashing). Vocabulary table size/shuffle operations — trivially small (142 words, O(n) Fisher-Yates). The exam module's own timer discipline (`renderSequentialMatch`, `examTick`, `exitExam`) is correct and can serve as the reference implementation for fixing P3.

## Critical Issues for Phase 3 Context

- Both Phase 2 reviews independently converged on the same uncancelled-timer / unmanaged-SpeechRecognition-lifecycle root cause already flagged in Phase 1 (H2/A2/A9) — this is now confirmed from three independent angles (correctness, architecture, and performance/security) and is the single highest-value fix in the codebase. Testing review should prioritize a regression test/manual repro script for "navigate away mid-round, mid-speech-recognition, mid-exam-part."
- S1/S2 (HTML injection via `innerHTML`) and P1/P4 (SpeechRecognition lifecycle, dead service worker) are the concrete, fixable items or documentation review should note as gaps: the README's "nothing is persisted" claim (S6) is factually wrong post-exam-subsystem and should be corrected as part of any documentation pass.
- No blocking Critical/High-severity security issues exist; no P0 fixes are required before shipping to the intended single-device audience.
