# Phase 2: Security & Performance Review

**Scope:** HookHub codebase (see `00-scope.md`), plus the parent monorepo's `.github/workflows/` where relevant since hookhub's CI/automation lives there. Security audit verified live response headers, ran `npm audit`, and cross-referenced catalog/candidates data. Performance analysis re-ran `npx next build` and confirmed Phase 1's measurements independently.

## Security Findings

**Executive summary:** The web app itself has no Critical/High findings — no API routes, no middleware, no Server Actions, no database, no auth, no dangerous sinks (`dangerouslySetInnerHTML`, `eval`, etc. — all verified absent). Risk is concentrated in the **CI/CD supply chain**: an unattended, scheduled, `contents: write`-scoped workflow consuming attacker-controlled external data (arbitrary GitHub repo names/descriptions/topics) with several fail-open gates.

### Medium
- **#1 (CVSS 6.6) — Unpinned third-party GitHub Action + write-scoped token in unattended workflow.** `hookhub-source-discovery.yml` (and other workflows) reference actions by mutable tag (`@v4`, `@v7`) rather than pinned commit SHA. A compromised action (precedent: `tj-actions/changed-files`, March 2025) would run with `contents: write` + `pull-requests: write` on a public repo whose `main` auto-deploys to production. Fix: pin to commit SHAs, add Dependabot for `github-actions` ecosystem.
- **#2 (CVSS 5.3) — Fail-open validation: malformed API fields bypass every admission gate.** `daysAgo()` returns `NaN` on unparseable dates; every relational comparison against `NaN`/`undefined` is `false`, so missing `stargazers_count`/`pushed_at` defeats both the minimum-star floor *and* the `MAX_PLAUSIBLE_STARS` anti-fake-star ceiling simultaneously. Fix: validate/coerce at the API boundary, fail closed on malformed shape.
- **#3 (CVSS 5.0) — Trust boundary derived from a UI display flag** (`official: true`). 134 of 290 catalog entries carry this flag, expanding a 1-org hardcoded seed into a 75-org allowlist that gets a 10× lower star bar and 4× longer staleness window in the discovery bot, plus a `foundVia: "known-org"` provenance label the human curator relies on as a trust signal. Not exploitable today (attacker can't set `official` or create repos in `microsoft`/`aws-samples`), but real risk paths exist: GitHub namespace reuse after an org rename/deletion silently and permanently grants low-bar automated access; a cosmetic "add the badge" edit silently grants an entire org's namespace CI-trust with no reviewer awareness the field does double duty. Fix: extract an explicit `TRUSTED_ORGS` allowlist pinned to numeric org IDs (not names, which GitHub releases on rename), gated by CODEOWNERS.
- **#4 (CVSS 5.4) — Public `@claude` workflow trigger has no workflow-level author gate.** Repo is public; any GitHub user can open an issue containing `@claude` and trigger a job with `id-token: write` and the repo's OAuth token before the underlying action's own permission check runs. Mitigated in practice by `claude-code-action@v1`'s internal actor check, but that check is delegated to a third-party action pinned to a mutable tag (compounds #1). Fix: add `author_association` gate at the workflow `if:` level.
- Architecture review's finding A5 (75-org trust allowlist derived from `official`) and this security finding #3 are the same underlying issue examined from two angles — converges independently, reinforcing it as real.

### Low
- **#5 (CVSS 3.7) — Dynamic `import()` of `data/catalog.ts`/`candidates.ts` executes them as code**, not data, inside a job holding `contents: write` and a live token. Not currently exploitable (bot only ever writes via `JSON.stringify`-escaped fields), but a single smuggled top-level statement in a "data-only" PR — the exact PR class reviewers are primed to skim — yields code execution with repo-write, in the same file the bot rewrites weekly. Fix: switch to JSON + inert parsing, or read+parse instead of `import()`; drop the discovery job to `contents: read` with `persist-credentials: false`.
- **#6 (CVSS 3.1) — Curation "rejected" status has zero enforcement — confirmed live in production.** Cross-referencing confirmed `aws-samples/sample-claude-code-agent-team` is marked `rejected` in `candidates.ts` yet published as 5 live catalog entries, one carrying `official: true` (which feeds finding #3's trust allowlist). This is the same data-integrity defect Phase 1's architecture review flagged (A4) — now confirmed as a genuine security-relevant gate failure, not just a data-hygiene issue: the only human safety gate in the pipeline is advisory and has already been silently violated.
- **#7 (CVSS 3.1) — Missing security response headers.** No CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy (verified via live `curl -sI`). Low practical impact given no auth/cookies/state-changes, but recommended as defense-in-depth for a site fed by external, less-trusted data.
- **#8 (CVSS 3.1) — Unanchored `github.com` substring matching** in both `item-card.tsx:44` (link-label spoofing, e.g. `github.com.evil.io`) and `find-new-sources.mjs:103`'s `extractOrg` (a `repoUrl` merely *containing* `github.com/microsoft/` anywhere, including a query string, injects `microsoft` into the CI trust allowlist from #3). Fix: parse via `new URL()` and check `hostname` exactly, not substring match.
- **#9 (CVSS 2.0) — `nanoid <3.3.18` transitive advisory** (GHSA-2v37-7h3g-55p8), reachable only via `postcss` at build time with a fixed non-zero size — negligible real risk, but no Dependabot/scheduled `npm audit` exists to catch the *next* one.
- **#10 (Info) — `Access-Control-Allow-Origin: *`** on HTML documents; harmless for this public, cookie-free site, but flagged because README references a sibling Vercel alias with SSO enabled — confirm the wildcard isn't inherited there.
- **#11 (Info) — One unquoted numeric interpolation** in the candidate-file code generator (`stars: ${item.stars}`, no coercion) — the only sink `serializeCandidate` doesn't route through `JSON.stringify`.
- **#12 (Info) — Insufficient logging/monitoring (OWASP A09)** — same root cause as Phase 1's H3/B1: total API outage is indistinguishable from a quiet week; no request timeout either.
- **#13 (Info)** — No `SECURITY.md`, no `CODEOWNERS` (notable since the catalog itself lists security tooling).

**Verified non-findings** (checked and cleared, worth recording): XSS via `<a href={item.repoUrl}>` is mitigated by React 19's built-in `javascript:`-URL blocking plus `rel="noopener noreferrer"`; no TS source-injection via bot-written descriptions (`JSON.stringify`-escaped); no SSRF (hardcoded API host); `candidates.ts` is never imported by the rendered app; full-tree secret scan clean; no dangerous sinks anywhere; `claude-code-review.yaml` correctly uses `pull_request` (not `_target`) so fork PRs get no secrets.

## Performance Findings

Verified via a fresh `npx next build`: `catalogItems` = 290 entries (111,525 B raw source / 22,696 B gzip); client chunk carrying the full catalog = 98,137 B raw / **23,302 B gzip**; prerendered `index.html` contains only 51/290 items (17.6%); Tailwind CSS output is a non-issue at 7,773 B gzip.

### Critical
- **Entire 290-entry catalog shipped to every client regardless of active tab.** Confirms and quantifies Phase 1's H1/A1 exactly: `app/page.tsx`'s `"use client"` pulls all `catalogItems` into the client bundle; only 17.6% of the catalog is server-rendered/crawlable. `ItemCard` has zero interactivity (no hooks, no handlers) yet hydrates on every one of up to 114 instances per tab for no UX benefit. **Recommended fix, evaluated against alternatives**: convert `app/page.tsx` to a Server Component driven by `searchParams` (not `next/dynamic` per-tab code-splitting, which still ships full tab JSON and doesn't fix crawlability) — this is the only option that removes catalog data from client JS entirely, fixes crawlability to 100%, and makes every type/tag combination its own indexable, prerenderable URL.

### High
- **Discovery script's sequential fetch loop has no timeout and query count scales 1:1 with catalog size forever.** Every new `official: true` catalog entry permanently adds one more query + 2.1s delay to every future weekly run (currently 75 orgs + 12 topics ≈ 87 requests, ~183s delay floor alone, already close to GitHub's 30 req/min secondary limit). Same root cause as security finding #1/#2 and Phase 1's H3/M8, now framed as an operational scaling risk: this only gets worse as the catalog succeeds at its purpose.
- **Client-bundle-everything architecture degrades linearly and increasingly badly as the catalog grows.** At current ~385 bytes/entry, projected growth to 1,000 entries (plausible given ~10 new candidates/week observed in commit history) would ship ~384 KB raw / ~80 KB gzip of pure data to every visitor regardless of which single tab (17–20%) they view — the *percentage* of crawlable content would also shrink. Resolved entirely by the Critical fix above (client payload becomes O(items shown) instead of O(total catalog)).

### Medium
- `stars` counts are frozen snapshots with no refresh path for existing catalog entries (only new candidates get a star fetch) — genuine staleness issue, not just cosmetic, since counts only grow and readers have no way to know how stale a number is. Same as Phase 1's M12/B6.
- No retry/backoff on transient GitHub API failures — any non-OK response permanently drops that query's results for the week with no distinction between "rate limited, retry" and "real error."
- Unguarded read-modify-write race on `data/candidates.ts`: no file lock, no atomic temp-file+rename, so two overlapping script runs (manual `workflow_dispatch` racing the cron) could silently lose one run's candidates or leave the file mid-write/invalid.
- No pagination/virtualization for large tabs — at 1,000+ items in a single type (plugin is already 114/290 ≈ 39%), the current single-grid render mounts everything at once with no windowing.

### Low
- No `useMemo` on derived filter arrays (`itemsOfActiveType`, `availableTags`) — harmless at n=290 today but no guard against a future feature (e.g. search-as-you-type) making this recompute per keystroke.
- Fragile list key `item.repoUrl + item.name` with no separator — same as Phase 1 L15, now independently reconfirmed; recommend switching to `key={item.repoUrl}` alone once A3's identity work lands, or at minimum add a separator.
- Unused `font-bold` (700) weight loaded via `next/font` (5 `.woff2` files, 164 KB total build output) — never referenced in rendered CSS; browsers won't fetch it, but it's dead build output.
- `data/candidates.ts` grows monotonically with no pruning path (154 pending + 3 rejected today, ~10/week growth) — slow, not urgent, but worth a cap/archive strategy eventually (same as Phase 1's B3).

## Critical Issues for Phase 3 Context

1. **The `"use client"` client-boundary bug is now confirmed Critical from three independent angles** (code quality, architecture, performance) with measured production-build numbers. This is the single highest-priority fix in the whole review and should anchor the final report's top recommendation. It also means **testing coverage should specifically target**: (a) that a future fix doesn't regress crawlability/SSR coverage, and (b) that the filter/tab logic behaves correctly whichever fix pattern (Server Component + searchParams) is chosen.
2. **The `aws-samples/sample-claude-code-agent-team` "rejected but live" contradiction is now confirmed as both a data-integrity defect (Phase 1's A4) and a security-relevant control failure (security finding #6)** — the curation "rejected" gate has zero enforcement and has already been silently violated in production. Testing/Docs review should check whether any test or CI step could plausibly catch this class of defect, and documentation review should check whether the curation workflow docs (README, candidates.ts header) accurately describe what enforcement actually exists (currently: none).
3. **The `official: true` UI-flag-as-trust-boundary issue (Phase 1's A5, security finding #3) has no test coverage and is undocumented as a security control** — worth flagging in Phase 3's documentation review as a case where the *security implications* of a data field are invisible to whoever edits it next.
4. **CI (`hookhub-ci.yml`) runs only lint + build** — neither catches any of the data-integrity defects (A3/A4/finding #6) or the fail-open validation gaps (finding #2). This is a direct input to Phase 3's test-coverage review: the single highest-value test in this repo, per both Phase 1 and Phase 2 independently, is a data-validation script wired into CI.
